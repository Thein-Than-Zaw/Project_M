# Database schema / migration plan v0.1 — DRAFT

Source: requirements v1.1 §5.11.3, D01–D06 and DEV-01/02/03 authorization. Executable scope: V1–V3 foundation, V4–V6 identity, V7–V9 pairing. Other entities remain draft. Full-feature schema is NOT READY FOR DEVELOPMENT pending relevant decisions; implemented increments are separately testable.

## DEV-03 implemented pairing increment

V7 adds unique membership(space_id,user_id) support and pairing_invitation: UUID PK, space FK, same-space creator membership FK, unique SHA256 token hash, created/expires/consumed/revoked instants, optional consumed_by user FK, matching consumed timestamp/actor check, partial unique unconsumed/unrevoked invitation per space. V8 adds pairing_confirmation keyed by user_id FK, invitation FK, unique hash, expected shared date/version, expiry. Each new preview replaces the actor's prior preview. V9 adds pairing_join_receipt keyed by user_id with UUID idempotency_key, SHA256 semantic request hash, space_id and same-space membership FK. No raw code stored. Confirmations for successful join deleted inside same transaction; receipts persist with membership for safe retries. Unpair/delete/receipt retention lifecycle is not introduced. Standard Flyway history only; no extra migration ledger.

All pairing writes lock existing registration_gate(id1) in consistent order before state checks. Space+creator membership and join+consume+receipt/version update are atomic. Invitation and preview validity use PostgreSQL clock_timestamp() after acquiring the gate so expiration during lock wait is rejected (transaction-start CURRENT_TIMESTAMP would be stale). WAITING/ACTIVE is derived from1/2 persistent memberships, never socket/presence state. No migration modifies original signup dates or seeds couple members. Post-commit event is a live hint; PostgreSQL membership remains authoritative after restart.

## DEV-02 forward migration increment

V4__add_account_security_state.sql adds app_user.enabled (boolean defaulttrue) and security_revision (BIGINT default0, nonnegative). No account deletion/replacement policy is selected. Every authenticated HTTP request verifies enabled/revision against its principal. V5__create_registration_gate.sql creates and seeds the singleton lock row(id=1), not a business account. V6__create_registration_token.sql stores UUID PK, kind SETUP/PARTNER CHECK, SHA-256 token_hash CHAR64 unique, nullable issued_by FK, created/expires/consumed/revoked timestamps, valid expiry and kind/issuer consistency checks. Partial unique index allows only one unconsumed/unrevoked code per kind. Issuance revokes old codes, including expired rows, before replacement. Register locks gate→validates capacity/code→inserts account→consumes token in one transaction. Existing V1–V3 are unchanged. This token is registration eligibility, distinct from future Couple Space invitations.

## DEV-05 physical schema addition

V12__create_chat_conversation.sql: space_id UUID PK/FK→couple_space, last_sequence BIGINT nonnegative, updated_at timestamptz; created lazily under concurrent-safe INSERT ON CONFLICT, then FOR UPDATE. V13__create_chat_message.sql: UUID PK, space_id FK→conversation, positive sequence, sender_id with same-space membership composite FK, client_message_id UUID, Unicode body length1–4000/nonblank constraint, created_at/delivered_at/read_at timestamptz. Unique(space_id,sequence), unique(sender_id,client_message_id), read_at implies delivered_at; partial unread index(space_id,sender_id,sequence) WHERE read_at IS NULL. No fixture/real accounts seeded or existing data rewritten by migrations. V1–V11 immutable; private pre-upgrade backup and before/after original-table fingerprints recorded separately.

Ordered allocation/message insert commit atomically; DB failure rolls counter/message back. Receipt updates hold same conversation lock and verify actor is recipient (peer sender), never accept client user/space. Timestamps per-message deliberately preserve unread older history when only latest page/viewport is read. No separate cursor/notification table is pretended to provide exact receipts. Body never changes after insertion through current APIs; no edit/delete/upload/retention lifecycle. Retention/account replacement remain separate Q03 decisions. Forward fixes preferred; automatic table dropping/old backup restore would lose new messages and is not a safe recovery guarantee.
