# DEV-03 Pairing — scoped working contract

Source: v1.1 F02 PAIR-01–03/AC-F02-01–06, D01/D02/D04/D05/D06; owner confirms Myanmar timezone and one-time persistent Messenger-like pairing, then asks to continue. Pairing persists in PostgreSQL; logout, partner offline and restart never unpair. Current Q03 lifecycle remains deferred; no unpair/delete/replacement API.

Scope: create single space, explicit join preview/confirmation, expiring/regenerable hashed invitation, atomic two-member join with durable same-intent idempotency, member-only REST/home metadata and own-user STOMP pairing events, session/socket revocation, responsive real UI. Paired login routes directly to a real minimal shared-home landing. Full F03 dashboard/profile, counters (Q02), chat/gifts/memories/calls/notification inbox remain later tasks. PostgreSQL installer work is independent; keep current portable DB until owner says installed setup is ready. Preserve pre-existing Git/README merge conflict; do not stage/resolve unrelated work.

Flow: unpaired login→space setup→creator confirms date (prefilled original signup date)→WAITING→generate pairing code→partner signs up through DEV-02 registration eligibility if needed, logs in→enters pairing code→preview shows inviter/shared date/own signup date/timezone→explicit confirmation→ACTIVE→both home. Registration code and pairing code are separate and clearly labeled; no automatic membership from signup. A creator may explicitly correct the initial shared date before creation; original signup date remains unchanged. Later shared-date changes are DEV-04, not silent overwrite during join.

Engineering defaults from source proposal: random256-bit pairing code, hash only,24h lifetime; regeneration revokes old unused code; confirmation valid10min and bound to actor/invite/space-version/date; principal-derived actors; no user/role/space routing trusted from body. Date must be valid four-digit LocalDate not after today in confirmed Asia/Yangon. Event timestamps UTC. Membership counts derive WAITING1/ACTIVE2; presence never alters pairing. Global registration gate reused as consistent single-deployment transaction lock (signup/create/invite/preview/join); database singleton/slots/FKs remain native guards.

REST implemented plan: GET /api/space→UNPAIRED own setup metadata or own WAITING/ACTIVE summary; POST /api/spaces `{relationshipDate,confirmed:true}`→201 summary (repeat same existing creator/date safely returns own waiting space); POST /api/invitations→201 `{code,expiresAt}` only waiting member; POST /api/invitations/preview `{code}`→200 inviter/shared date/own signup date/timezone/confirmationToken/expires; POST /api/invitations/join `{code,confirmationToken,confirmedRelationshipDate,confirmed:true}` + UUID Idempotency-Key→200 summary. Identical actor/key/semantic intent replay returns original membership; altered key/payload is409, used/expired/revoked/self/foreign rejects without mutations. Timeout reconciles GET /api/space before retry. GET /api/home and /home.html require ACTIVE own membership; no arbitrary space-ID read endpoint. CSRF all writes, configurable pairing rate/IP limits; sensitive codes in bodies only.

WS: native /ws authenticated same-session handshake with explicit localhost origins; required STOMP CONNECT CSRF. Only waiting/active members subscribe literal /user/queue/pairing; no arbitrary user/broker topics, no client SEND destinations. Event `{eventId,type:'pairing.updated',serverTimestamp,state:'ACTIVE'}` sent to member user queues only AFTER_COMMIT, containing no private date/name content. Client re-fetches authorized summary; reconnect/readiness fallback GET reconciles missed events. Live HTTP session validity + enabled/revision + membership enforced inbound/outbound; logout/expiry closes socket, periodic sweep handles idle/disable. No offline/durable broker claim; DB summary is authoritative.
